## 二、已证实：发布不会让线上站点切换工作流

**结论：一个 app_id 永久只 serve 它第一次绑定的那个 workflow。**

复现过至少 6 次，覆盖源应用、市场克隆和若干测试应用：
- 改草稿 → 发布 → 发布接口返回 200 且 `app.workflow.id` 已更新，
  但站点跑的一直是旧 workflow（用 `/api/chat-messages` 读 `workflow_finished.data.workflow_id` 确认）。
- 重置站点访问令牌**不会**重新绑定。
- 只有**换一个新 app_id** 才能拿到新流程。

因此：
- 公开站点 `iFz58NDJdGkzfwSZ` 绑定在工作流 `0492fc53-cfd1-45ca-87a5-c26999da3683` 上，
  此后在 `f2e4f2a5` 里做的所有改动都到不了用户面前。
- 在控制台对该应用再点"发布"是**无效动作**，不要再试。
- 要让用户用上新流程，必须：新建应用 → 复制工作流 → 发布 → 确认绑定 →
  换新 URL → 重新出二维码 → 更新材料里所有引用。这属于对外动作，需先确认。

### 可靠的"开一个可测新应用"流程

1. `POST /console/api/apps/{DST}/copy` 得到新 app_id
2. 立刻 GET 源应用草稿 → GET 新应用草稿
3. POST 新应用草稿（带源应用的 graph + 新应用的 hash）
4. 发布
5. 轮询新站点的 live workflow_id 直到等于刚发布的那个
6. 不等就重来（复制动作会触发一次异步自动发布，可能抢先绑定）

脚本：`spinfresh.js`（1-5 步）+ `poll.py`（第 5 步轮询）。

## 三、已证实：跨轮次状态传不进去（三条路全部证伪）

这决定了面试状态机只能怎么写。

| 尝试的路 | 结论 | 证据 |
| --- | --- | --- |
| 会话变量 | **写入不落库** | 变量赋值节点全部 `succeeded`，但 `GET /console/api/apps/{id}/conversation-variables?conversation_id=X` 读回 7 个变量仍是默认值 |
| 大模型记忆 | **历史从未注入** | 受控实验：首轮告知学校专业，次轮留空 `user_major`/`user_skills` 问适配岗位，模型答"你这次没有提供专业、技能和意向城市"。给 7 个节点补 `role_prefix` 无变化 |
| 系统变量 | **提示词里解析不到** | 提示词里探测 `{{#sys.dialogue_count#}}`、`{{#sys.conversation_id#}}`，模型回执均为空。虽然 `workflow_started` 的 inputs 里看得见 `sys.dialogue_count`，但提示词层取不到 |

### 因此面试状态机改成"无历史"版

面试官提示词不依赖任何历史，只从用户**本条消息的内容类型**推断进度：

- 题型顺序固定：自我介绍 → 专业能力 → 项目/实习深挖 → 行为面试(STAR) → 岗位理解/职业规划
- 类型 → 进度：开始=0，继续=1，跑题=1，自我介绍=1，专业能力=2，项目经历=3，行为面试=4，岗位理解=5，兜底=3
- 一条消息同时命中多个类型时，取最大的那个进度
- **三条铁律**：除用户明确说"重新开始/换个岗位再面一次"外，进度永不为 0、永不重出第 1 题；进度只前进不倒退；拿不准答到第几题时，选一个比"自我介绍"更靠后的题型往下问，不要从头再来

实测（余额耗尽前）：干净流程 0→1→2→3→4→5 全通并出复盘报告；面试中被"三方协议违约怎么办"打断能正确切到政策分支；回来喊"继续面试"能从原进度续上而不是重新开始。

### 顺带拆掉了纯消耗的死链

按依赖关系逐个查消费方，发现面试分支尾部是一条**只烧额度、不产出**的链：

```
模拟面试官 → 面试进度提取(参数提取) → 写入面试进度 → 写入目标岗位 → 写入面试状态 → 回复
```

- 「面试进度提取」的三个输出只被那三个赋值节点消费
- 三个赋值节点只写会话变量，而会话变量已证实从不落库
- 这些变量唯一的读者是「面试续答守卫」，所以守卫从来就没生效过
- 回复节点的模板本来就是 `{{#1791552000021.text#}}`，直接引用面试官的输出，压根不过这条链

已删除这 4 个节点，改为「模拟面试官 → 回复」直连。删除前后做过结构校验：
节点 29→25、边 25、无孤立点、从开始节点全部可达、面试官到回复节点连通。

**效果**：面试分支每轮从 3 次模型调用降到 2 次，和岗位、政策分支拉平。省下的这次调用直接降低 DeepSeek 额度消耗——
余额耗尽和每轮多次调用是相关的。

> 备份：改动前的完整图在 `graph_backup_20261010.json`（29 节点），要还原直接用里面的 graph 存回草稿。

### 分类器同步改为内容判定

- 类别名从短标签改回**携带消歧规则的描述式长名**（短名会让模型丢掉规则，实测更差）
- 指令补"判断顺序（命中即停）+ 关键区分示例"
- 明确一两个字的短承接语（嗯/好的/继续/下一题/我知道）归「面试陪练」，**不算寒暄**——
  这是短承接语被误送进闲聊兜底的修法

  已改为让参数提取节点直接产出检索式。
- 参数提取节点的 query 选择器用三段路径（开始节点 ID + sys + query）解析不稳定，
  改两段 `sys.query` 后稳定。
- 问题分类节点不消费对话历史，面试中的作答会被误分类。
- 平台三项能力不可用：数据库节点（UDMS 超时）、长期记忆库（后端不完整）、
  Python 代码节点（沙箱段错误），均按手册的降级路径处理。
- 站点与工作流永久绑定：发布新流程不会让线上地址切换，重置令牌也不行，
  只有换 app_id 才行。这个结论复现了 6 次以上，直接影响"地址什么时候必须定稿"。
- 会话变量写入是空操作、大模型记忆历史从未注入、系统变量在提示词里取不到——
  三条跨轮次状态的路全部实测证伪，见第三节。
